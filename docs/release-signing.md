# Подпись обновлений

Установщик и его SHA-256 лежат в одном релизе GitHub. Контрольная сумма ловит
битую загрузку, но не подмену: кто может править релиз, заменит оба файла.
Подпись закрывает это. Приложение проверяет Ed25519-подпись файла
`notetaker-v<версия>-windows-x64-setup.exe.sha256` ключом, который зашит в бинарник.

Пока ключа нет, `SIGNING_KEY` в `crates/runtime/src/update.rs` равен `None`:
приложение подпись не требует, job `sign` в релизе ничего не делает.

## Включение

Приватный ключ создаёт и хранит владелец проекта. В репозиторий он не попадает.

1. Создать приватный ключ Ed25519 в формате PKCS#8 PEM:
   `openssl genpkey -algorithm ed25519 -out <файл-ключа>`.
   Копию сохранить в менеджере паролей.
2. Положить его в секрет репозитория:
   `gh secret set UPDATE_SIGNING_KEY --repo IvanKhramov/notetaker < <файл-ключа>`.
3. Получить публичный ключ:
   `openssl pkey -in <файл-ключа> -pubout -outform DER | tail -c 32 | xxd -p -c 64`.
   Вписать эти 64 hex-символа в `SIGNING_KEY` как `Some("...")` и выпустить релиз.

Начиная с этого релиза job `sign` подписывает контрольную сумму и кладёт рядом
файл `.sha256.sig`. Если ключ в секрете не совпадает с зашитым или секрета нет,
job падает и релиз остаётся черновиком.

## Что важно знать

- Версия с зашитым ключом ставит только подписанные обновления. Релиз без
  подписи такие клиенты не примут.
- Потеря приватного ключа: выпустить обновление для этих клиентов нельзя,
  версию с новым ключом придётся ставить вручную. Поэтому копия ключа нужна
  вне GitHub.
- Секрет GitHub нельзя прочитать обратно, его получает только job `sign`.
  В этом job нет сторонних actions.
- macOS-сборку приложение само не ставит, там подпись не проверяется.

## Подготовка релиза

Каждый release PR добавляет в CHANGELOG.md раздел своей версии с датой
и изменениями для пользователя. Workflow берёт этот раздел для заметок релиза.
Если раздел отсутствует, GitHub генерирует заметки автоматически.
